- 과제명: Tiny Second-hand Shopping Platform
- 개발 목적: 중고거래 플랫폼의 최소 기능을 구현하면서 개발 생명주기 전 과정에서 시큐어 코딩을 적용한다.
- 개발 환경: Python 3.10+, Python 표준 라이브러리, SQLite, HTML/CSS, WSGI
- GitHub: `[GitHub 저장소 URL]`
- AI 활용: 요구사항 구체화, 위협 모델링, 코드 초안, 테스트 케이스 작성, 문서 구조화에 생성형 AI를 활용했다. 단, 생성 코드의 권한 검사·SQL 처리·CSRF·세션 처리·송금 로직을 직접 검토하고 테스트했다.

## 2. 요구사항 분석

### 2.1 기능 요구사항

1. 사용자는 회원가입·로그인·로그아웃을 할 수 있어야 한다.
2. 사용자는 상품을 등록하고 전체 상품과 상세 내용을 볼 수 있어야 한다.
3. 사용자는 상품명과 설명을 기준으로 상품을 검색할 수 있어야 한다.
4. 사용자는 다른 사용자에게 1:1 메시지를 보낼 수 있어야 한다.
5. 사용자는 의심스러운 상품 또는 사용자를 신고할 수 있어야 한다.
6. 사용자는 가상 포인트를 다른 사용자에게 송금할 수 있어야 한다.
7. 관리자는 사용자 정지·해제, 상품 숨김·복구, 신고·메시지·송금 감사 내역 조회를 할 수 있어야 한다.

### 2.2 비기능 요구사항

- 사용자 입력을 서버에서 검증한다.
- 비밀번호를 평문으로 저장하지 않는다.
- 인증된 사용자와 관리자 권한을 구분한다.
- SQL Injection, XSS, CSRF, IDOR, 세션 고정 공격을 방어한다.
- 별도 패키지 없이 실행할 수 있도록 재현성을 확보한다.
- 오류 발생 시 내부 정보나 스택 트레이스를 사용자에게 노출하지 않는다.

### 2.3 요구사항 변경

- **실제 송금 → 가상 포인트 송금**: 실제 금융 거래는 PG사 연동, TLS, 본인 인증, 법적·회계적 통제, 부정거래 탐지까지 필요하다. 과제 범위에서 불완전한 실제 결제를 구현하면 오히려 보안 위험이 커지므로 가상 포인트로 변경했다.
- **실시간 전체 채팅 → 1:1 메시지**: 최소 기능을 안정적으로 검증하기 위해 서버 푸시가 필요한 실시간 채팅 대신 데이터베이스 기반 메시지로 구현했다.
- **신고 누적 자동 정지 → 관리자 검토 후 차단**: 자동 정지는 다중 계정과 허위 신고로 정상 사용자를 공격할 수 있으므로 중복 신고를 막고 관리자가 최종 조치하도록 변경했다.

## 3. 시스템 설계

### 3.1 아키텍처

```text
브라우저
  ↓ HTTP 요청
Python WSGI 애플리케이션(app.py)
  ├─ 라우팅 및 화면 생성
  ├─ 인증/세션/CSRF
  ├─ 입력 검증 및 권한 검사
  ├─ 상품/메시지/신고/송금/관리자 로직
  ↓ 파라미터 바인딩 SQL
SQLite 데이터베이스(tiny_market.db)
```

### 3.2 데이터베이스

- `users`: 아이디, 표시 이름, 비밀번호 해시, 포인트 잔액, 활성 상태, 관리자 여부
- `sessions`: 난수 세션 토큰, 사용자 ID, CSRF 토큰, 만료 시각
- `products`: 판매자, 상품명, 설명, 가격, 이미지 URL, 판매·숨김 상태
- `messages`: 발신자, 수신자, 연관 상품, 메시지 내용
- `reports`: 신고자, 대상 유형, 대상 ID, 사유, 처리 상태
- `transfers`: 송신자, 수신자, 금액, 처리 시각

### 3.3 주요 권한 정책

- 비로그인 사용자는 상품 조회·검색만 가능하다.
- 상품 등록·메시지·신고·송금은 로그인 사용자만 가능하다.
- 상품의 판매 상태 변경과 삭제는 판매자 본인 또는 관리자만 가능하다.
- 사용자 정지와 상품 숨김은 관리자만 가능하다.
- 사용자는 자신에게 메시지·송금·신고할 수 없다.

## 4. 구현

### 4.1 회원 관리

- 사용자 아이디는 영문·숫자·밑줄 3~20자로 제한했다.
- 비밀번호는 10자 이상이며 대문자·소문자·숫자를 포함하도록 했다.
- 비밀번호는 `hashlib.pbkdf2_hmac`으로 난수 Salt와 함께 310,000회 반복 해시했다.
- 로그인 성공 시 세션 토큰을 새로 발급해 세션 고정 공격을 줄였다.

### 4.2 상품 및 검색

- 상품명 2~80자, 설명 5~2,000자, 가격 0~100,000,000 범위를 검증한다.
- 이미지 URL은 `http`와 `https`만 허용한다.
- 검색은 SQL 문자열 연결이 아니라 `LIKE ?` 파라미터 바인딩을 사용한다.
- 상품명·설명 출력 시 HTML 특수문자를 이스케이프한다.

### 4.3 메시지와 신고

- 메시지는 1~500자로 제한하고 송수신자를 서버에서 다시 확인한다.
- 한 사용자가 같은 대상을 반복 신고하지 못하도록 데이터베이스 UNIQUE 제약을 적용했다.
- 신고 결과는 관리자 페이지에서 확인하고 사용자 정지 또는 상품 숨김 조치를 한다.

### 4.4 포인트 송금

- 송금액은 1~1,000,000 포인트의 정수만 허용한다.
- 본인 송금, 존재하지 않거나 정지된 사용자 송금, 잔액 초과를 거부한다.
- `BEGIN IMMEDIATE` 트랜잭션 안에서 송신자 차감·수신자 증가·내역 생성을 함께 수행한다. 중간 오류 시 전체를 롤백한다.

### 4.5 관리자

- 관리자 전용 페이지에서 사용자 상태, 상품 공개 상태, 신고 목록과 최근 메시지·송금 감사 내역을 조회한다.
- 관리자 여부를 URL이나 화면 표시가 아니라 데이터베이스의 `is_admin` 값과 서버 측 권한 검사로 확인한다.

## 5. 개발 중 확인한 보안 약점과 수정

| 보안 약점 | 초기 위험 | 변경 내용 | 결과 |
|---|---|---|---|
| 평문 비밀번호 저장 가능성 | DB 유출 시 즉시 계정 탈취 | PBKDF2-SHA256 + 난수 Salt 적용 | 평문 복구가 어렵고 사용자별 해시가 다름 |

| 로그인 후 기존 세션 유지 | 세션 고정 | 로그인 성공 시 기존 세션 삭제 후 토큰 재발급 | 공격자가 심은 세션 재사용 방지 |
| 음수·잔액 초과 송금 | 잔액 증가 또는 데이터 불일치 | 정수·범위·잔액 검증과 DB 트랜잭션 | 비정상 금액 차단, 원자성 확보 |

## 8. 유지보수

### 8.1 확인한 개선점

- 현재 Rate Limit은 단일 프로세스 메모리에 저장되므로 서버 재시작 시 초기화된다.
- SQLite는 소규모 과제에는 적합하지만 동시 접속자가 많은 서비스에는 한계가 있다.
- 이미지 URL은 외부 도메인에서 직접 로드되므로 개인정보 추적이나 깨진 링크 문제가 생길 수 있다.
- HTTPS는 애플리케이션 자체가 아니라 실제 배포 환경의 리버스 프록시에서 적용해야 한다.

### 8.2 향후 개선 계획

1. Redis 기반 분산 Rate Limit 적용
2. PostgreSQL 전환과 마이그레이션 도입
3. HTTPS 리버스 프록시, Secure Cookie, HSTS 기본 활성화
4. 이미지 파일 서버 저장 시 확장자·MIME·크기 검증과 무작위 파일명 적용
5. 관리자 신고 처리 사유와 감사 로그 추가
6. 메시지 읽음 상태와 차단 사용자 기능 추가
7. 자동화된 정적 분석과 CI 테스트 추가

## 10. 결론

모든 요구 기능을 단순히 추가하는 것보다, 기능을 구현하는 각 단계에서 입력 검증·권한 검사·세션·데이터 일관성을 함께 설계하는 것이 중요했다. 특히 AI가 생성한 코드도 보안 요구사항을 별도로 제시하고 테스트하지 않으면 평문 비밀번호, CSRF 누락, IDOR, 송금 검증 누락과 같은 약점이 남을 수 있다. 본 프로젝트는 과제 범위 안에서 재현 가능한 최소 플랫폼을 구현하고 주요 웹 보안 약점을 코드와 테스트로 완화했다.
